追一个 tokenizer shift 的 bug，追到第 40 轮，模型把已经用 4 个探针排除过的路径又跑了一遍。钱和时间都花了，结论还是原来那个。它在那一刻确实不知道自己在第 12 轮就排除过这条路，因为那段历史在上一次压缩里被摘要成了一句「排查了 tokenizer 相关问题」。

摘要没有写错，问题在于它把「试过什么」和「结论是什么」揉进同一句，丢掉了「在哪个 commit、哪个后端、什么 dtype 下成立」这个前提。3 轮之后模型把这条结论拿去用了，而那时我已经换过分支。

这篇文章只讨论给 agent 做长程排查记忆这一层，不涉及上下文压缩算法本身，也不评价具体 harness 的实现。代码是 DeepSeek Harness 的一个插件，Node 24，零原生编译依赖。

## 三种失效形状与它们的共同点

类似事故我后来归了类，可复现的有三种。

第一种是压缩后遗忘：已经排除的路径被摘要掉，模型重新踩一遍，也就是开头那次。

第二种是假设升格成事实。某次推理里我写过一句「大概是权重同步路径的问题」，纯粹是直觉。2 轮之后它进了摘要，再过 2 轮，模型已经在说「确定是权重同步问题」，中间没有任何实验支持。

第三种更隐蔽：条件变了，结论没变。结论本身没错，但它是某个 commit、某个后端、某个量化档位下的结论。切分支之后它就不再是事实，可它在上下文里长得跟事实一模一样。

这三种的表面差异很大，共同点在于同一件事：结论与它的可信度和适用条件脱钩了。压缩是有损操作，而有损压缩会优先丢掉限定语，因为限定语看起来像冗余。丢掉的恰好是判断一条结论还能不能用所必需的那部分。

## 三个自然方向为什么不成立

第一个念头是向量库。把排查记录 embedding 进去，需要的时候按相似度捞回来。

这个方向我很快自己否掉了。相似不等于适用：一段文字跟当前任务语义接近，完全可能是因为它讲的是同一个模块的旧版本问题。向量相似度不知道 commit 已经变了，也不知道这条结论来自另一种后端。它擅长找相关文字，而我要回答的是这条结论现在还能不能用，这两个问题的答案经常相反。

第二个念头是让模型在压缩时写一份「排查纪要」带上。试过，失败方式比原来更隐蔽：模型写纪要时会自然地把不确定的东西写得更确定，一份纪要产出之后，下一轮没人知道哪句话有证据、哪句是猜的。信息量没减少，只是全部被拉平到同一个可信度。

第三个念头是不压缩，历史全留着。token 账算不过来。

三个方向错在同一处：都默认要记住的对象是对话。真正需要留下的东西比对话小得多，也硬得多。

## 该建模的是发现

排查过程中真正可复用的是有限几类东西：观察到什么、诊断出什么、有什么约束、做了什么决定、下一步做什么。每一类都自带证据和适用范围。

所以 Finding Ledger 存的是 finding，不是消息也不是文档。一条 finding 有主张、有来源、有适用条件、有状态、有演化历史，落在本地一个 SQLite 文件里。它和工作日志的分工是：日志管事件顺序和任务归属，`AGENTS.md` 管 agent 该守的规矩，设计文档管系统形状；而「发现、证据、适用范围」这三件事此前没有归属，所以单独做一层。

## 一条结论要同时回答三个不相关的问题

这是我改动时间最长的部分。最早 schema 里只有一个 `status` 字段，取值是 `active`、`inactive` 之类。

问题在于它得同时回答三个互不相关的问题：现有证据支持还是反驳这条主张；这条记录在账本里处于什么位置；在当前这个项目、版本、环境下能不能直接使用。

这三个问题的答案可以任意组合。一条被反证的假设很可能仍是「当前」的，我还在这个假设的坟头上继续排查；一条被取代的旧结论可能在旧版本上依然正确；「本轮实验只用 GPU 0-3」这种用户约束在证据强度上谈不上支持或反驳，但必须被遵守。塞进一个字段，就只能靠约定俗成去表达组合，而模型会自己发明组合。

拆成的三个维度各自管一件事：`epistemic_state` 管证据（支撑、反证、有争议、未评估等），`lifecycle_state` 管它在账本里的位置（现行、被取代、撤回、归档），applicability 管这次任务能不能用。前两个是存下来的静态字段，第三个不是，它每次检索时按当前上下文重新计算。

沿这条线有三处我明确拒绝的设计，都指向同一条判断：不许把不确定性藏起来。

`epistemic_state` 里没有 `verified`，也没有 `user-confirmed`。这两个值看起来方便，实际会把「谁说的」和「证据多少」压成一个字段。一旦存在 `user-confirmed`，模型会把它当作证据升级的捷径，而用户确认过的也可能只是用户的猜测。用户陈述我单独存成一种来源类型（`user_statement`），它是一条来源，不是结论本身；没有证据支撑的主张，状态只能是 `provisional`。同理，`source_kind = log` 也不等于可信，代码可能被读错，日志可能采集不全，实验可能有混杂因素。

`refuted` 不等于 `superseded`。被反证的假设通常仍处在现行生命周期里，它是「已排除路径」而不是垃圾。长程排查里两类知识同样值钱：知道正确做法，和知道哪条路走不通。删掉后者，模型就会一次次回到已经排除的分支，这正是开头那次事故。反过来，被取代的结论也不一定错，它可能只是适用于旧版本，所以取代只降级它在当前任务里的地位，不抹掉它在历史中的正确性。

条件不明确不许默认适用。判断不了就落到 `unknown` 或 `needs_revalidation`。这里诱惑很大：把缺失字段默认当成匹配成功，注入的召回率数字会更好看。但那样等于把不确定性藏进统计口径里，而这个项目的全部价值恰恰是把不确定性显式留住。

## 数据结构如何支撑这些判定

一条 finding 的可信度不能靠「句子写得像事实」制造，因此证据不能塞在 finding 的某个文本字段里。账本里有两张表专门管证据：一张描述来源本身（类型、定位符、文件修订号、片段、内容哈希），另一张描述这份来源对某条主张起什么作用，支持、反驳还是仅作背景。同一条日志可以支持 A 的同时反驳 B，这个关系压不成 evidence 表上的一列布尔值。

另有一条跨表约束必须由服务层实现：标记为 `supported` 的记录至少要有一条支撑证据。SQL 的 `CHECK` 表达不了跨表计数，于是「不许空口标 supported」从 schema 兜底提升成代码里必须通过的一关。

检索部分我一版就用了确定性规则，没有 embedding，也没有 reranker。流程是：先建任务上下文，取 project_id、当前目标、branch、commit、后端、dtype 和剩余 token 预算，取不到的字段标 `unknown` 而不是让模型猜；然后做四类硬过滤，分别是项目隔离、排除被取代与归档记录、排除标记为永不注入的记录、排除 scope 硬冲突；接着给候选按适用性、检索策略、任务相关性、认知状态等几个键排序；最后按预算裁剪并格式化，每条注入带 finding ID、主张、认知状态、适用条件和一句证据摘要与来源定位。

这里有一处容易写错：被反证且仍处现行的记录不能被过滤掉，它就是「已排除路径」的来源。

我也没有做模型自填的 0 到 1 置信度。那个数字既不可校准也不可审计，加进来只会让注入结果看起来更精细。向量检索留在评测回路里：等人工标注的回归集证明关键词召回确实不够，再上 embedding。现在没有证据支持这一步，提前上等于给自己找一个不可解释的故障源。

## 形态与兜底

插件形态是被需求逼出来的：排查的连续性发生在会话内部，「上下文压缩完成」这个时机只有宿主看得见，脱离宿主事件就不存在正确的注入点。所以它做成 DeepSeek Harness 的 bundle patch，订阅装配点，在新会话、恢复会话、压缩完成和账本修订号变化这几个时机重新注入。

底层用 Node 24 内置的 `node:sqlite` 而不是 `better-sqlite3`。后者是原生模块，需要编译或者依赖预编译产物匹配当前平台与 ABI，对不上就是安装失败；内置模块让整个包保持零原生编译依赖。选 SQLite 而不是服务端数据库，是因为排查记录是本地、单人、写少读多的数据，一个文件足够，顺带少一条敏感日志外流的路径。

还有一条兜底原则值得写进设计：注入链路出现任何异常，只降级为「这次不注入」，绝不阻塞用户手上的主任务。记忆层没资格让排查停下来。

安全边界按「不确定就少做」处理：本地优先存储，只留定位符和必要摘要，密钥与私密路径脱敏或拒绝落盘，项目隔离默认关闭跨项目检索。另有一条容易被忽略的：证据是数据，不是指令。来源可能是外部网页、日志或用户粘贴的内容，里面的「请执行……」一律不许当提示词用。

## 现在的状态

四个阶段里，可信数据层完成，项目与 scope 可靠性完成，宿主集成与预算化注入主体完成；评测回路没做，向量检索没上。

离线测试用 `node:test` 覆盖了状态机、事务原子性、项目隔离、密钥脱敏、适用性判定和注入格式。这些测试能证明行为符合契约，证明不了它到底省了多少事。我现在给不出「重复排查下降百分之多少」这样的数字，要拿到它需要一个人工标注的回归集，跑几轮真实排查，对比开与不开。这件事排在评测阶段，我没有提前编数据的兴趣。

代码在 [github.com/Aression/Finding-Ledger](https://github.com/Aression/Finding-Ledger)，设计契约在仓库 `docs/design/` 下的 7 份文档里，开头先列用户故事和验收标准，MIT。如果要给自己的 agent 加一层记忆，我的建议是先数一数自己被压缩坑掉过几次，再决定记忆应该长什么样。
